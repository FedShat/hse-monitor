# SmartLMS → Telegram

Монитор записи на независимый экзамен по английскому в ВШЭ. Python 3.11+, aiogram 3,
aiohttp, SQLite. На сервере не нужны браузер, Selenium, Redis или открытые входящие порты.

## Быстрый запуск

В текущей рабочей папке `.env` уже содержит `MoodleSession`, импортированную из Chrome.
**Не перезаписывайте этот файл копированием `.env.example`.** Добавьте в него:

```dotenv
TELEGRAM_BOT_TOKEN=токен_от_BotFather
TELEGRAM_CHAT_ID=ваш_числовой_ID
```

Отправьте `/start` боту со своего Telegram-аккаунта. Для новой установки сначала
скопируйте `.env.example` в `.env` и заполните cookie и Telegram-параметры.

```bash
chmod 600 .env
docker compose build
docker compose run --rm monitor inspect
docker compose up -d
docker compose logs -f --tail=100
```

`inspect` только читает LMS: **не записывает в слот, не отправляет Telegram-сообщения,
не меняет сохранённый снимок мониторинга**, независимо от настроек автозаписи.

Локально с uv:

```bash
uv sync --frozen
uv run python -m hse_monitor inspect
uv run python -m hse_monitor
```

Или установите `requirements.txt` в virtualenv и запускайте `python -m hse_monitor`.

## Копирование на сервер

Из локальной папки проекта:

```bash
./scripts/sync.sh --dry-run user@server:/home/user/hse-monitor/
./scripts/sync.sh user@server:/home/user/hse-monitor/
```

Скрипт переносит `hse_monitor/*.py`, `Dockerfile`, `compose.yaml`, `requirements.txt`,
`.dockerignore`, `.env.example`, README и **локальную `.env`**. Локальная `.env` заменяет
серверную и получает на сервере права `600`; без локальной `.env` скрипт завершится с ошибкой.
База, virtualenv, тесты и кеши не передаются. Существующие файлы на сервере не удаляются.
Нужны SSH-доступ и rsync с обеих сторон; родительская папка назначения должна существовать.
Для нестандартного порта: `RSYNC_RSH='ssh -p 2222' ./scripts/sync.sh user@server:/path/`.

Настройки и cookie редактируйте в локальной `.env`, затем запускайте синхронизацию.
После синхронизации выполните в серверной папке:

```bash
docker compose up -d --build --force-recreate
```

Сам скрипт только копирует файлы, запуск контейнера выполняется этой командой отдельно.
Импорт cookie из Chrome выполняется локально на Mac; следующий запуск `sync.sh` перенесёт
новое значение на сервер. `--force-recreate` применяет обновлённую `.env` к контейнеру.

## Автозапись

По умолчанию включён мониторинг, автозапись выключена. Для настоящей записи:

```dotenv
AUTOBOOK_ENABLED=true
AUTOBOOK_DRY_RUN=false
```

```bash
docker compose up -d --force-recreate
```

Если ранее отправляли `/autobook off`, настройка сохранена в SQLite и имеет приоритет
над `AUTOBOOK_ENABLED`. В этом случае также отправьте `/autobook on`.
С `AUTOBOOK_DRY_RUN=true` бот только сообщает, какой слот выбрал бы, и не отправляет POST.

Без фильтров подходит любой **будущий** слот с местами и активной кнопкой Register.
Выбирается ближайший по дате. Можно задать ID в порядке предпочтения, регулярное
выражение для названия и включительные границы дат/времени:

```dotenv
SLOT_IDS=
SLOT_NAME_REGEX=
DATE_FROM=2026-11-02
DATE_TO=2026-12-31
TIME_FROM=09:00
TIME_TO=18:00
TZ=Europe/Moscow
```

Пустые значения отключают соответствующее ограничение. Все заданные фильтры действуют
одновременно. Изменение таблицы отслеживается целиком; фильтры ограничивают сообщения
о доступных местах и выбор для записи. Истёкшие даты никогда не используются для записи.

Перед записью загружается свежая HTML-форма. Бот отправляет один POST и проверяет наличие
формы отмены (`mode=off`) у выбранного слота. Сам по себе HTTP 200 не считается успехом.
После подтверждения одной записи автозапись выключается; существующая запись тоже
блокирует новые. Бот не отменяет и не переносит записи.

Если ответ потерялся, запрос записан как `pending` в SQLite **до** отправки.
Повторного POST после тайм-аута или перезапуска не будет. Монитор продолжает проверять
результат чтением страницы. Если результат так и не подтвердился, проверьте LMS вручную;
только если записи нет, отправьте `/clear_pending`, затем `/autobook on`.

Успешная реальная запись пока не проверялась: свободных будущих слотов при разработке
не было. Формат POST взят из настоящей страницы; сценарии записи проверены на имитации LMS.
Если LMS добавит дополнительное подтверждение или изменит форму, бот остановит автозапись.

## Команды и уведомления

Команды принимает только указанный `TELEGRAM_CHAT_ID`, только в личном чате от того же
пользователя. Чужим пользователям бот не отвечает.

| Команда | Действие |
| --- | --- |
| `/status` | Последняя проверка, режим, ошибки, подтверждённая/неподтверждённая запись |
| `/slots` | Доступные слоты из последнего снимка |
| `/check` | Запросить проверку; не отменяет паузу и серверный Retry-After |
| `/pause`, `/resume` | Приостановить/продолжить мониторинг |
| `/autobook on`, `/autobook off` | Переключить автозапись, сохранив выбор между перезапусками |
| `/clear_pending` | После ручной проверки снять блокировку неопределённого результата |
| `/reload_auth` | Запросить проверку с cookie из `.env` при локальном запуске |

Разные сообщения: 🟢 можно записаться, 🔴 запись больше недоступна, 📋 изменились строки
таблицы, ✅ запись подтверждена, 🧪 пробная запись, 🔐 истекла/недействительна cookie,
🔓 восстановилась сессия, ⚠️ ошибка/неизвестный результат, 🟢 восстановилась связь.
При первом запуске уже доступные места тоже сообщаются.

Снимок, настройки, состояние записи и очередь сообщений сохраняются в SQLite на volume
`monitor-data`. Telegram отправляется отдельной задачей, поэтому его задержки не задерживают
POST записи. Неотправленные сообщения повторяются после сетевых ошибок и перезапуска.
При падении процесса между отправкой Telegram и подтверждением в SQLite возможен дубль
уведомления; повторная запись в слот этим механизмом не выполняется.

`POLL_INTERVAL=3` — целевой интервал между началами проверок, минимум 1 секунда.
Запросы последовательные, соединение переиспользуется; медленный сервер увеличивает
интервал. После ошибок применяется экспоненциальная задержка до `MAX_BACKOFF=300`,
а `Retry-After` сервера соблюдается и при большей длительности. Абсолютный приоритет
перед другими участниками не гарантируется.

## Сессия и секреты

Для исследованной страницы достаточно **одной** cookie `MoodleSession`.
Access token и пароль не требуются. Cookie отправляется только на хост LMS;
переходы к SSO автоматически не выполняются. `sesskey` извлекается из HTML, хранится
только в памяти и не попадает в SQLite, ссылки Telegram или логи.

Cookie должна находиться в `.env`:

```dotenv
LMS_COOKIE_HEADER='MoodleSession=значение'
```

Повторный импорт из авторизованной вкладки Chrome на macOS:

```bash
python3 scripts/import_chrome_cookie.py
```

Chrome: «Вид → Разработчикам → Разрешить JavaScript из событий Apple».
Скрипт сохраняет только `MoodleSession`, не читает остальные профили/пароли и не выводит
значение cookie. После импорта настройку Chrome можно отключить.

При локальном запуске обновлённая cookie автоматически перечитывается из файла.
В Docker Compose `.env` передаётся как переменные окружения: после его изменения нужен
`docker compose up -d --force-recreate` (обычный `restart` не обновит окружение).

`AUTH_REFRESH_INTERVAL=300` обновляет HTML и CSRF-ключ, **не обновляет истёкший SSO-вход**.
Автоматический вход через refresh token не реализован: для него нужен отдельно проверенный
SSO-поток. При истечении сессии бот присылает отдельное уведомление 🔐 с шагами обновления
cookie и перезапуска Docker, сохраняет старый снимок и повторяет проверки с задержкой.
Это уведомление отправляется один раз до успешного восстановления, в том числе после
перезапуска бота; состояние и сообщение сохраняются в SQLite. Разные ошибки входа не
создают повторных уведомлений о cookie. После успешной проверки бот присылает 🔓.
Войдите в LMS в браузере и импортируйте новую cookie.

`.env`, `.private/`, `data/` исключены из git; Docker-контекст допускает только исходники
приложения и файл зависимостей. Cookie и Telegram-токен не запекаются в образ.
Контейнер работает от непривилегированного пользователя с файловой системой только для
чтения; SQLite записывается в отдельный volume. Запускайте один экземпляр: локальный
file lock защищает общий STATE_PATH, но отдельные серверы/volumes его не разделяют.

## Найденный протокол SmartLMS

Проверено чтением страницы аккаунта 1 ноября 2026 года: 196 слотов, будущих доступных — 0.

1. `GET /mod/selfgrouping/view.php?tab=slot&id=1887331&lang=en` — HTML с `sesskey`.
2. Тот же путь с `download=json`, `sesskey`,
   `_qf__mod_selfgrouping_local_form_filter=1`, `currentnumberofgroup=0` — полный
   JSON-экспорт, массив таблиц `[[{...}, ...]]`, без пагинации наблюдаемого экспорта.
   На этой активности он занимал около 47 КБ против 900 КБ HTML.
3. `currentnumberofgroup=1` — фильтр Available groups only. Монитор использует полную
   таблицу, чтобы замечать изменения и не терять исчезнувшие строки.
4. `POST /mod/selfgrouping/userselfrecord.php` — форма с `cmid=1887331`,
   `id=<ID слота>`, `mode=on`, `sesskey=<свежий ключ>`. Допустимость определяется
   по настоящей кнопке формы, а не только по разнице вместимости и числа участников.

На странице есть прошлые слоты с местами и отключёнными кнопками, а также строка с
нулевой вместимостью. Поэтому старые даты и `capacity=0` не считаются доступными.
Нестабильные HTML ID, CSRF-ключи и порядок строк не создают уведомлений об изменении.

## Проверки

```bash
uv run pytest -q
uv run ruff check hse_monitor scripts tests
docker compose run --rm monitor inspect
```

Тесты не обращаются к LMS/Telegram и используют вымышленные секреты. Они проверяют
парсер, ограничения, различение свободного места и активной кнопки, повторные уведомления,
подтверждение записи, неопределённый ответ, восстановление, Retry-After, очередь и доступ
к командам. Зависимости закреплены в `uv.lock` и `requirements.txt`.

Документация используемого Telegram-механизма:
[aiogram long polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html).
